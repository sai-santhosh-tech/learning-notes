2) How to prevent Memory leak issue in java

MEMORY LEAK :- Objects Which are no longer required, but present in memory(heap,meta space) and Garabage collector is unable to remove them.

Common Causes of Memory Leaks

1. Unclosed Resources
Resources such as database connections, file streams, and sockets consume memory and system resources.

2. Static fields live as long as the class lives — leading to memory leaks if you store objects unnecessarily.
public static List<User> userList = new ArrayList<>(); // Bad

3. Collections grow but don’t shrink automatically. Clear large maps/lists when done
	list.clear(); 
	map = null;
4. Improper Cache Implementation
Caches that grow without limit can exhaust memory.
5. Careful with Inner Classes / Anonymous Classes : They hold implicit references to outer classes
6. Monitor the Memory using Memory Leak Detection Tools like VisualVM, JProfiler etc
	
3) How to handle failures in MICROSREVICES

@Hystrix annottaion
   Use libraries like Resilience4j to protect from downstream failures: Circuit Breaker, Retry, Fallback
	
	@Service
	public class OrderService {

		private final RestTemplate restTemplate;

		public OrderService(RestTemplate restTemplate) {
			this.restTemplate = restTemplate;
		}

		@CircuitBreaker(name = "productService", fallbackMethod = "getDefaultProduct")
		@Retry(name = "productService")
		public String getProductDetails(String productId) {
			String url = "http://localhost:8081/products/" + productId;
			return restTemplate.getForObject(url, String.class);
		}

		// Fallback method: same signature + Throwable as last parameter
		public String getDefaultProduct(String productId, Throwable t) {
			return "Fallback Product: No data available for productId=" + productId;
		}
	}


	@GetMapping("/{id}")
	public String fetchProduct(@PathVariable String id) {
			return orderService.getProductDetails(id);
	}
	RETRY Config : 
	resilience4j.retry.instances.productService.max-attempts=3
	resilience4j.retry.instances.productService.wait-duration=2s

	How It Works
		On calling /orders/123, OrderService contacts ProductService.
		If ProductService fails:
			1) Retry 3 times (2 seconds apart).
			2) If still fails → circuit breaker opens.
			3) Fallback method is called.

9) How to schedule a task in spring boot ?
	Steps to Schedule a Task
	1) Enable Scheduling using @EnableScheduling 
	2)Create a Scheduled Method: Use @Scheduled on any @Component, @Service, or @Configuration bean
		@Component
		public class MyScheduledTask {

			@Scheduled(fixedRate = 5000) // runs every 5 seconds
			public void runEveryFiveSeconds() {
				System.out.println("Task executed at: " + java.time.LocalDateTime.now());
			}
		}
	| Annotation                                           | Description                                        |
| ---------------------------------------------------- | -------------------------------------------------- |
| `@Scheduled(fixedRate = 5000)`                       | Executes every 5 sec **after the last start time** |
| `@Scheduled(fixedDelay = 5000)`                      | Executes 5 sec **after the last completion**       |
| `@Scheduled(initialDelay = 10000, fixedRate = 5000)` | Starts after 10 sec, then every 5 sec              |
| `@Scheduled(cron = "0 0/1 * * * ?")`                 | Cron expression (every 1 min in this case)         |
	
	@Scheduled(fixedRate = X)
		Next execution starts X ms after the previous execution STARTED
		Runs at a regular interval, regardless of how long the task takes (can overlap if not finished)

	@Scheduled(fixedDelay = X)
		Next execution starts X ms after the previous execution COMPLETED
		Ensures a fixed pause between completions

For a job that should run every day at 1:00 AM, the cron expression depends on the format your system uses.

✅ Standard Spring Boot / Quartz (6 fields)
0 0 1 * * *

Meaning:
0 → seconds
0 → minutes
1 → hour (1 AM)
* → every day of month
* → every month
* → every day of week

✔ Runs daily at 1:00 AM

10) What is marker interface & its use case with an example
	A marker interface is an interface that has no methods or fields. It is used to mark or tag a class to indicate that it should be handled in a 
	special way by the JVM or a framework.
	Ex :- Serializable, cloneable etc
	Real-World Use Case: Auditing System
	Imagine you have a system where only certain entities should be audited (e.g., stored in an audit log).
	Step 1: Define the Marker Interface
	public interface Auditable {
    // Marker interface — no methods
	}
	Step 2: Mark Specific Classes
	public class User implements Auditable {
		private String username;
		private String email;
	}

	public class Product {
		private String name;
		private double price;
	}
	Only User is auditable.
	Step 3: Auditing Logic Using Marker Interface
	public class AuditLogger {

    public void logChange(Object obj) {
        if (obj instanceof Auditable) {
            System.out.println("Auditing: " + obj.getClass().getSimpleName());
            // Save audit info to DB or log
        } else {
            System.out.println("Skipping audit for: " + obj.getClass().getSimpleName());
        }
    }
}

12) What Are Varargs in Java ?
	Varargs (Variable-Length Arguments) allow you to pass zero or more arguments to a method. Instead of defining multiple overloaded methods, 
	you can use varargs to accept any number of parameters of the same type.
	Use Cases :- 
	| Use Case                                               | Example                                                                  |
| ------------------------------------------------------ | ------------------------------------------------------------------------ |
| When number of arguments can vary                      | Logging, calculations, string utilities                                  |
| To simplify APIs that used overloaded methods          | E.g., `printf(String format, Object... args)`                            |
| To avoid manually creating arrays when calling methods | `someMethod("a", "b", "c")` vs `someMethod(new String[]{"a", "b", "c"})` |

	JDK Example: String.format() :- format(String format, Object... args) uses varargs to accept dynamic arguments.
	String formatted = String.format("Name: %s, Age: %d", "Sai", 25);
Rules & Limitations :-
	1. Only one vararg allowed per method
	void method(String... names, int... ages); // ❌ Compile error
	2. Must be the last parameter
	void method(String prefix, String... names); // ✅
	void method(String... names, String suffix); // ❌ Compile error

13) What is an Idempotent Method in REST?
	In REST, an idempotent method is a method that can be called multiple times without changing the result beyond the first call.
	Example: 
	1) PUT is Idempotent (GET,DELETE also Idempotent)
	PUT /user/123
	Body: { "name": "Sai", "age": 30 }
	a) First call: updates or creates user 123 with new data.
	b) Second call: same input, same effect — no additional change.
	2) POST is NOT Idempotent
	POST /user
	Body: { "name": "Sai", "age": 30 }
	a) First call: creates user with a new ID.
	b) Second call: creates another user with the same data — not idempotent.
	✅ Why Idempotency Matters
	1) Safety: Helps avoid side effects from retries (e.g., network timeouts).
	2) Resilience: Used in distributed systems and APIs with retry logic.


	PUT vs PATCH
	🔥 1. What’s the core difference?
	👉 PUT = full update (replace the resource)
	👉 PATCH = partial update (modify only some fields)

	PUT   /users/101   → replace entire user  
	PATCH /users/101   → update only given fields 

	🔥 2. Is PUT always required to send all fields?
	👉 Ideally yes (by definition)
	PUT is meant to replace the entire resource.

	❗ If you send partial data with PUT:
	Missing fields may become null or reset
	Behavior becomes ambiguous

	🔥 3. Can PATCH update multiple fields?
	👉 Yes ✅
	PATCH can update one or many fields

	🔥 4. Which one is idempotent?
	👉 PUT → always idempotent
	👉 PATCH → not guaranteed

	🎯 Perfect Interview Summary =>
	👉 PUT is used for full resource replacement and is idempotent, whereas PATCH is used for partial updates and may or may not be idempotent depending on implementation.

17) Define sealed class or interface (Java 17 feature) ?
	Sealed classes/interfaces are like saying: "Only these few classes are allowed to extend/implement me — no one else!"
	
	NOTE :- All subclasses are final classes only, if don't need to be final then make it non-sealed
	Example :
	1️) Payment.java – Sealed Interface
	public sealed interface Payment permits CreditCardPayment, UpiPayment, WalletPayment {
		void pay(double amount);
	}
	
	2) CreditCardPayment.java – Final class
	public final class CreditCardPayment implements Payment {
     @Override
     public void pay(double amount) {
        System.out.println("Paid ₹" + amount + " using Credit Card.");
     }
   }
   3) UpiPayment.java – Final class
   public final class UpiPayment implements Payment {
	 @Override
	 public void pay(double amount) {
        System.out.println("Paid ₹" + amount + " using UPI.");
     }
   }
   
   4) PaymentProcessor.java – Runner
	public class PaymentProcessor {

    public static void main(String[] args) {
        processPayment(new CreditCardPayment(), 1000);
        processPayment(new UpiPayment(), 500);
        processPayment(new WalletPayment(), 300);
    }

    static void processPayment(Payment payment, double amount) {
        payment.pay(amount);

        // Example of instanceof + pattern matching (Java 16+)
        if (payment instanceof UpiPayment upi) {
            System.out.println("Logged: Paid via UPI");
        }
    }
	
	| Keyword      | Meaning                                                    |
| ------------ | ---------------------------------------------------------- |
| `sealed`     | Base class/interface, restricts subclasses                 |
| `permits`    | Lists the allowed subclasses                               |
| `final`      | Subclass can’t be extended                                 |
| `non-sealed` | Subclass lifts the restriction (can be extended by anyone) |

FlexiblePayment.java — non-sealed
public non-sealed class FlexiblePayment implements Payment {
    @Override
    public void pay(double amount) {
        System.out.println("Paid ₹" + amount + " using a flexible method.");
    }
}

This class can be override now, as it is non-sealed class.

Benefits of SEALED CLASS :-
1)  Explicit control over subclassing
2)  Good for pattern matching (switch expressions or instanceof block): As compiler knows all subclasses)


18) DELETE vs TRUNCATE
| Feature                   | `DELETE`         | `TRUNCATE`          |
| ------------------------- | ---------------- | ------------------- |
| Removes All Rows?         | ✅ (if no WHERE)  | ✅ Always            |
| Conditional Deletion?     | ✅ (uses `WHERE`) | ❌ No                |
| Rollback Possible?        | ✅ Yes            | ⚠️ Depends on DB    |
| Fires Triggers?           | ✅ Yes            | ❌ No                |
| Speed                     | Slower           | Faster              |
| Resets Auto-Increment?    | ❌ No             | ✅ Yes (in most DBs) |
| Logged in Transaction Log | ✅ Fully          | ❌ Minimally         |

DELETE :
The space (pages/blocks) in the table is not immediately released to the database.
Instead, that space is marked as available for reuse within the same table.

TRUNCATE :
TRUNCATE deallocates memory (or storage space) immediately, and is ideal for quickly clearing a table completely.

@Configuration

    basePackages = "com.example.secondary.repository",
    entityManagerFactoryRef = "secondaryEntityManagerFactory",
    transactionManagerRef = "secondaryTransactionManager"
)
public class SecondaryDBConfig {

    @ConfigurationProperties("spring.datasource.secondary")
    public DataSource secondaryDataSource() {
        return DataSourceBuilder.create().build(); // Manually created
    }

    @Bean
    public LocalContainerEntityManagerFactoryBean secondaryEntityManagerFactory(

                .dataSource(secondaryDataSource())
                .packages("com.example.secondary.entity")
                .persistenceUnit("secondary")
                .build();

    public PlatformTransactionManager secondaryTransactionManager(
            @Qualifier("secondaryEntityManagerFactory") EntityManagerFactory emf) {
        return new JpaTransactionManager(emf);
    }
}

20) Difference between Class.forName(String className) and ClassLoader.loadClass(String className)

Class.forName(String className)  : Loads the class and also initializes it (i.e., runs static blocks).
ClassLoader.loadClass(String className) : Loads the class but does NOT initialize it (i.e., static blocks are NOT executed).

Use Class.forName("ClassName") when you want to both load and initialize the class immediately.
Use ClassLoader.loadClass("ClassName") when you want just loading, and handle initialization separately or later.

If the class is not found, the method throws a ClassNotFoundException.


ClassNotFoundException vs NoClassDefFoundError
| ClassNotFoundException                                                                       | NoClassDefFoundError                                           |
| -------------------------------------------------------------------------------------------- | -------------------------------------------------------------- |
| Checked Exception                                                                            | Error                                                          |
| Occurs while loading a class explicitly using `Class.forName()` or `ClassLoader.loadClass()` | Class was available at compile time but missing at runtime     |
| Must be handled or declared                                                                  | Not required to handle                                         |
| Example: `loadClass("ABC")` when ABC doesn't exist                                           | Application starts, but a dependent class/JAR is removed later |

21) what is FUTURE in Java ?
Future is an interface introduced in Java 5 (with java.util.concurrent package). It represents the result of an asynchronous computation — something that will finish later.

Think of it like a promise:
“You will get the result later when the task finishes.”

		✅ Basic Use Case
		You submit a task to a thread or executor, and get a Future<T> in return.
		You can then:
			a) Check if it’s done
			b) Wait for the result(.get())
			c) Cancel it if needed
	
	Key Methods in Future :
	
	| Method                          | Description                                                     |
| ------------------------------- | --------------------------------------------------------------- |
| `get()`                         | Waits (blocks) until result is available.                       |
| `get(timeout, unit)`            | Waits for result up to timeout, else throws `TimeoutException`. |
| `isDone()`                      | Returns `true` if task is completed.                            |
| `isCancelled()`                 | Returns `true` if task was cancelled.                           |
| `cancel(mayInterruptIfRunning)` | Tries to stop the task.                                         |


❌ Limitations of Future
1. get() is blocking.
2. Cannot chain multiple asynchronous operations.
3. No built-in exception handling.
4. Difficult to combine multiple futures.
That’s why Java 8 introduced CompletableFuture, which overcomes all of these.


		import java.util.concurrent.*;

		public class FutureExample {
			public static void main(String[] args) throws Exception {
				ExecutorService executor = Executors.newSingleThreadExecutor();

				Future<String> future = executor.submit(() -> {
					Thread.sleep(2000); // Simulate long task
					return "Task Completed";
				});

				System.out.println("Doing other work...");

				// Get result (waits if not done)
				String result = future.get(); // Blocks until done
				System.out.println("Result: " + result);

				executor.shutdown();
			}
		}
		
		✅ When to Use Future
			Use it when:
				a) You're using Java 5–7
				b) You just need to run tasks in background and wait for result
				c) You don’t need chaining, timeout handling, or reactive flows

22) what is COMPLETABLEFUTURE in java?
	CompletableFuture was introduced in Java 8 as part of the java.util.concurrent package. It is used for asynchronous, non-blocking programming, allowing tasks to 
	run in separate threads and enabling chaining of operations.
	
	It usaually increases the asynchronous programming capabilities.

	Using CompletableFuture
			CompletableFuture<String> future =
					CompletableFuture.supplyAsync(() -> {
						return "Hello";
					});

			System.out.println(future.get());
			Here, the task executes asynchronously using the common ForkJoinPool.
	1. Chaining Operations  => thenApply()
			Used to transform the result.

			CompletableFuture<String> future =
				CompletableFuture.supplyAsync(() -> "Java")
								 .thenApply(str -> str + " Developer");

			System.out.println(future.get());

		Output:
		Java Developer
	2. Consuming Results  => thenAccept()
		CompletableFuture.supplyAsync(() -> "Spring Boot")
						 .thenAccept(System.out::println);

		Output:
		Spring Boot
	3. Combining Multiple Futures   => thenCombine()
			CompletableFuture<String> first =  CompletableFuture.supplyAsync(() -> "Hello");
			CompletableFuture<String> second = CompletableFuture.supplyAsync(() -> " World");
			CompletableFuture<String> result = first.thenCombine(second, (a, b) -> a + b);
	4. Exception Handling   => exceptionally()


	✅ Scenario:
	You have two simulated APIs:
    getUserDetails() – takes 2 seconds
    getOrderDetails() – takes 3 seconds	
    You want to run both in parallel, and then combine their results.
	With custom executor: We can provide your own thread pool,
		public class CompletableFutureExample {

			public static void main(String[] args) throws InterruptedException, ExecutionException {
				ExecutorService executor = Executors.newFixedThreadPool(2); // Custom thread pool

				CompletableFuture<String> userFuture = CompletableFuture.supplyAsync(() -> getUserDetails(), executor)
					.orTimeout(3, TimeUnit.SECONDS)
					.exceptionally(ex -> "User API failed: " + ex.getMessage());

				CompletableFuture<String> orderFuture = CompletableFuture.supplyAsync(() -> getOrderDetails(), executor)
					.orTimeout(4, TimeUnit.SECONDS)
					.exceptionally(ex -> "Order API failed: " + ex.getMessage());

				// Combine both results
				CompletableFuture<String> combined = userFuture.thenCombine(orderFuture, 
					(user, order) -> "Combined Result: \n" + user + "\n" + order);

				// Print the result when all are done
				combined.thenAccept(System.out::println).join();

				executor.shutdown();
			}

			// Simulated API call
			public static String getUserDetails() {
				sleep(2000); // 2 seconds
				return "User: Sai Santhosh";
			}

			public static String getOrderDetails() {
				sleep(3000); // 3 seconds
				return "Order: MacBook Pro";
			}

			private static void sleep(int millis) {
				try {
					Thread.sleep(millis);
				} catch (InterruptedException e) {
					throw new IllegalStateException(e);
				}
			}
		}
	
	What is ForkJoinPool in Java?
     ForkJoinPool is a specialized thread pool introduced in Java 7 (java.util.concurrent) for executing tasks using the Fork/Join framework.
	 It is designed for:
			a) Parallel processing
			b) Divide-and-conquer algorithms
			c) Efficient utilization of CPU cores

	Why is it called Fork/Join?
    Fork  : Break a large task into smaller subtasks.
	Join  : Combine the results of the subtasks.
	
	Key Feature: Work Stealing
    Unlike a normal thread pool, ForkJoinPool uses a work-stealing algorithm.
	Suppose:
	Thread-1 Queue: [TaskA, TaskB]
    Thread-2 Queue: []
    If Thread-2 becomes idle, it can "steal" work from Thread-1's queue.
	Benefits:
		Better CPU utilization
		Reduced thread idle time
		Improved performance for parallel tasks

NOTE => ForkJoinPool is the default executor used by CompletableFuture.supplyAsync() when no custom executor is provided.

Why use a Thread Pool instead of new Thread()?

Creating a thread for every task is expensive because thread creation and destruction consume CPU and memory. 

A thread pool:

 a) Reuses existing threads.
b) Limits the maximum number of concurrent threads.
c) Improves performance and scalability.
d) Simplifies thread lifecycle management.

1. Fixed Thread Pool => ExecutorService executor = Executors.newFixedThreadPool(3);
2. Cached Thread Pool => ExecutorService executor = Executors.newCachedThreadPool();
3. Single Thread Executor => ExecutorService executor = Executors.newSingleThreadExecutor();
4. Custom Thread Pool =>  You can configure the pool size and queue using ThreadPoolExecutor.

ExecutorService executor = new ThreadPoolExecutor(
        2,                      // Core pool size
        5,                      // Maximum pool size
        60, TimeUnit.SECONDS,   // Keep alive time
        new LinkedBlockingQueue<>(10)
);

What each parameter means
			Core Pool Size = 2
Initially, 2 threads are created.
			Maximum Pool Size = 5
At most 5 threads can exist.
			LinkedBlockingQueue<>(10)
If all core threads are busy, up to 10 tasks can wait in this queue.

28) VOLATILE vs ATOMIC

NOTE :- Every thread normally caches the varaibales locally for performance reasons.

		✅ volatile (USECASE : flags(state changes purpose))
		Ensures visibility, NOT atomicity

		🔸 What it does:
		a) Guarantees that reads and writes go directly to and from main memory, not from thread-local caches.
		b) Ensures visibility of changes to variables across threads.
		c) It does not provide atomicity for compound operations like count++.
		
	✅ Atomic classes (like AtomicInteger, AtomicDouble etc)
		Part of java.util.concurrent.atomic package
		Ensures atomicity AND visibility

		🔸 What it does:
		a) Provides atomic (indivisible) operations on single variables.
		b) Uses low-level CPU instructions (CAS - Compare and Swap) under the hood.
		c) Ensures both visibility and atomicity for operations.


| Feature                | `volatile`                          | `Atomic` (e.g., `AtomicInteger`) |
| ---------------------- | ----------------------------------- | -------------------------------- |
| Visibility guarantee   | ✅ Yes                               | ✅ Yes                            |
| Atomicity guarantee    | ❌ No                                | ✅ Yes                            |
| Use case               | Flags, simple state indicators      | Counters, accumulators, etc.     |
| CAS (Compare-And-Swap) | ❌ No                                | ✅ Yes                            |
| Performance            | Slightly better for visibility-only | May be slightly slower but safe  |


     🔸 When to Use What?
			Use volatile for:
			One-thread writes, others only read.
			Flags like isRunning, shutdownRequested.

			Use Atomic classes for:
			Counters (count++), accumulators.
			Multiple threads updating same variable.
	
	

		public class VolatileVsAtomic {

			static int normalCounter = 0;
			static volatile int volatileCounter = 0;
			static AtomicInteger atomicCounter = new AtomicInteger(0);

			public static void main(String[] args) throws InterruptedException {
				Thread[] threads = new Thread[10];

				// Create 10 threads that each increment the counters 1000 times
				for (int i = 0; i < 10; i++) {
					threads[i] = new Thread(() -> {
						for (int j = 0; j < 1000; j++) {
							// Normal counter (not thread-safe)
							normalCounter++;

							// Volatile counter (not atomic!)
							volatileCounter++;

							// Atomic counter (thread-safe)
							atomicCounter.incrementAndGet();
						}
					});
				}

				// Start all threads
				for (Thread t : threads) {
					t.start();
				}

				// Wait for all threads to finish
				for (Thread t : threads) {
					t.join();
				}

				System.out.println("Expected count: 10000");
				System.out.println("Normal counter:   " + normalCounter);
				System.out.println("Volatile counter: " + volatileCounter);
				System.out.println("Atomic counter:   " + atomicCounter.get());
			}
		}


		OUTPUT :
		Expected count: 10000
		Normal counter:   8321
		Volatile counter: 8390
		Atomic counter:   10000
		
✅ Key Learning:
normalCounter++ and volatileCounter++ are both not atomic.
atomicCounter.incrementAndGet() is atomic and thread-safe.


Why do we need Atomic variables?

AtomicInteger, AtomicLong, AtomicReference, etc., ensure atomicity by using CPU-level atomic instructions (such as Compare-And-Swap (CAS)) instead of using locks (synchronized).

Suppose two threads increment a normal integer.
count++;

This looks like one operation, but internally it is three operations:
1. Read count from memory
2. Increment it
3. Write it back

AtomicInteger count = new AtomicInteger(5);
count.incrementAndGet();

Internally, it uses Compare-And-Swap (CAS).

CAS works like this

Suppose:
Current value = 5

Thread-1 wants to increment.
It performs:

Expected = 5
New Value = 6

if(current == expected)
      replace with new value
else
      retry
	  

Example with two threads => 

Initial value
count = 5

Thread-1 Reads
Expected = 5
New = 6

Thread-2 Reads
Expected = 5
New = 6

Now Thread-1 executes CAS
Current = 5
Expected = 5
Match ✅
Update value to 6
Now the value becomes => count = 6

Now Thread-2 executes CAS
Current = 6
Expected = 5

Mismatch ❌
The update fails.

Thread-2 retries:
Read current = 6
Expected = 6
New = 7

CAS succeeds
count = 7


volatile does not ensure atomicity. It only ensures visibility (and ordering guarantees), not that a sequence of operations executes as one indivisible unit.

Example
class Counter {
    volatile int count = 0;

    public void increment() {
        count++;
    }
}

Even though count is volatile, the statement: count++;

is actually:
1. Read count
2. Add 1
3. Write count

If two threads execute increment() simultaneously:

Initial count = 5

Thread-1 reads 5
Thread-2 reads 5

Thread-1 writes 6
Thread-2 writes 6

Final count = 6 ❌
Expected = 7

The volatile keyword cannot prevent this race condition.

What volatile guarantees
If one thread writes: flag = true;

and another thread reads:
if (flag) {
    // ...
}
then the second thread is guaranteed to see the updated value without needing synchronization.

volatile boolean flag = false;
This is a common use case for volatile.

39) RUNNABLE vs CALLABLE
Runnable and Callable are both used to define tasks for threads in Java, but they have some important differences.

| Feature                      | Runnable                    | Callable               |
| ---------------------------- | --------------------------- | ---------------------- |
| Package                      | `java.lang`                 | `java.util.concurrent` |
| Introduced in                | Java 1.0                    | Java 5                 |
| Method                       | `run()`                     | `call()`               |
| Return value                 | No return value             | Returns value          |
| Can throw checked exception? | No                          | Yes                    |
| Used with                    | `Thread`, `ExecutorService` | `ExecutorService`      |
| Future support               | No direct result            | Returns `Future`       |

1. Runnable
Used when task does not need to return anything.

Example :
class MyTask implements Runnable {

    @Override
    public void run() {
        System.out.println("Runnable executed");
    }
}

Thread t = new Thread(new MyTask());
t.start();

2. Callable

Used when task needs to:
a) return result
b) throw checked exception

Introduced in concurrent package.

Example
import java.util.concurrent.Callable;

class MyTask implements Callable<Integer> {

    @Override
    public Integer call() throws Exception {
        return 100;
    }
}


ExecutorService executor = Executors.newFixedThreadPool(1);
Future<Integer> future = executor.submit(new MyTask());
Integer result = future.get();
System.out.println(result);

Why Callable cannot be used directly with Thread?
Because Thread constructor accepts only: Runnable not Callable.
So Callable is usually used with:
ExecutorService
Future


ExecutorService.submit() accepts both:
submit(Runnable)
submit(Callable)

But:
Runnable → Future<?> with null result
Callable → Future<T> with actual result
